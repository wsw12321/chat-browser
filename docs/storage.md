# 本机历史、备份和恢复

数据库 `webchat-local` 使用 Schema 1，与应用契约 1、附件策略版本分别管理。历史和附件是浏览器中的明文数据，本机档案只做分组。Key 不接受为存储设置，也不进入备份。能够访问该浏览器配置的人可能读取历史。

## 已实现的持久化边界

`@chat/local-store` 的八个 Store 与 `docs/plan.md` 第 11 节一致。查询显式限制 `profileId`；同档案内原件和规范化产物按真实 SHA-256 去重。哈希在进入事务之前重新计算，文字产物同时核对 UTF-8 Blob 与预览文字。附件、Blob、提取记录在同一事务提交；预算或真实 IndexedDB 错误导致整体回滚。

每轮先获得会话许可，再通过 `prepareGeneration` 同时保存用户消息、助手占位、生成记录及分支修订，事务成功后调用网站接口。`saveGeneration` 保存聚合后的正文与结束状态；调用页面负责最多每 500 ms 保存一次，以及结束时立即保存。存储失败时页面应停止网络请求，并让用户下载内存中的正文。该库没有网络请求和自动重试。

修改或重试使用显式 `parentId` 创建新消息链；`setBranch` 选择已有分支，旧消息不会被覆盖。`expectedRevision` 防止旧页面覆盖会话修订。发送预览同时保存所有实际使用附件的原件/规范化哈希和策略/解析器版本；`prepareGeneration` 在同一发送事务中核对这些绑定，防止另一标签页重新审查历史附件后继续发送失效快照。`getSetting/setSetting` 仅接受模型选择、持久化许可结果、会话上下文起点和排除附件 ID 的明确类型。

会话互斥优先持有 Web Lock，并同时登记 IndexedDB 租约；不支持 Web Locks 时使用 IndexedDB 原子租约。租约有效期 15 秒，每 5 秒续约。所有写入核对租约持有者和有效期。恢复过程保留仍存在 Web Lock 或有效同持有者租约的任务，只将失去持有者的 `preparing/streaming` 标为 `interrupted`。后台冻结导致租约失效的页面不能继续保存旧任务。BroadcastChannel 只发送变更通知，不包含正文、文件名或哈希。

应用预算为 200 MiB。实际 Blob 字节与 JSON 编码后的记录字节累计，再增加 20% 索引/序列化余量；80% 显示提醒，超预算事务回滚。浏览器配额仍可能更小，必须处理真实 `QuotaExceededError`。删除会话在事务中查找其他消息引用，最后引用删除后清理 Blob 与提取记录。未绑定消息的附件保留 24 小时，显式移除立即删除，过期孤儿在 `gc(profileId)` 清理；调用页面可以在进入档案后执行 GC。

## `.chatbackup` 格式

备份是未加密的 Store ZIP，最多 100 MiB、2000 个条目，累计条目实际字节也不得超过 100 MiB。导出器先检查大小和条目数，再用 Blob 拼接本地头、文件内容和中央目录，无需对所有附件生成一个完整的解压数组。

只允许以下路径：

- `manifest.json`：格式 `chatbackup`、备份版本 1、数据库 Schema 1、记录分片列表、Blob 的 SHA-256 与字节数。
- `records/000000.json` 等：每片最多 4 MiB，只含严格校验的会话、用户/助手消息、附件、提取信息与生成结果。
- `blobs/<64 位小写 SHA-256>.bin`：需要的原件和规范化产物，同一哈希只出现一次。

首版拒绝压缩 ZIP、加密、ZIP64、分卷、符号链接、额外字段、注释、重复路径和任何其他路径；不使用宽松 ZIP 解压回退。逐项对照中央目录与局部头、实际边界、方法、标记、尺寸和 CRC，并验证 Blob 哈希。JSON 先检查深度 16 和重复键，再按 strict Schema 校验，不接受 `system` 角色、工具执行项、凭证或任意配置。消息文字最多 512 KiB；原件仍按文件扩展名的原始上限检查。真正的格式审查由当前解析器回调执行。

导入之前预留现有数据与完整暂存数据同时存在的预算。导入分两遍读取最大 4 MiB 记录分片：第一遍保留引用图和有限元数据、验证完整性；第二遍分批事务写入带暂存 ID 的记录。全文不会全部保留为 JSON 对象。ID 全部重新映射，不覆盖原档案或同档案中现有的记录。循环父引用、失效消息/生成/附件引用和不需要的 Blob 均拒绝。

所有暂存记录在查询界面隐藏，完成标记与所有记录的发布在同一事务中提交。失败或取消删除暂存内容；每批写入刷新导入租约，启动时清理超时遗留暂存。已存在的已发布 Blob 可复用，取消不会删除它。

`importBackup` 支持当前解析器 `review(source, attachment, signal)` 回调。审查失败保留历史，将附件标为 `needs_review`。重新审查无损成功可恢复 `ready`；含损失的附件必须重新获得用户确认，备份中的确认和回调传入的旧确认均不继承。不传审查回调时全部附件保持不可发送，直到用户逐一重新检查。`reReviewAttachment` 保留附件 ID，但要求原件哈希与原引用一致；版本变化后更新绑定确认。

## 更新与恢复约束

Schema 1 只新增 Store，不清空数据。收到 `versionchange` 会关闭旧连接并调用页面通知；升级阻塞触发 `onBlocked`，提示关闭旧标签页。将来每个 Schema 版本必须新增增量迁移，不允许把 `deleteDatabase` 当作修复。遇到较新数据库版本时，可使用 `openLocalStore({readOnlyOnVersionError:true})` 或独立 `openRecoveryStore()` 打开兼容的八个 Store，只读查看和导出，返回 `readOnly:true`。只读 API 不允许恢复状态写入、删除、GC、导入或设置修改；不创建不存在的数据库，也不降级版本。不兼容的 Store/索引仍报错且保留原数据。自动测试通过额外新增 Store 的 Schema 2 验证只读导出和写入拒绝。初次发布没有实际上一版业务 Schema；后续升级仍必须补充真实迁移与字段兼容测试。

备份请妥善保存。清除站点数据、浏览器重装、设备损坏或隐私会话结束可能丢失记录。持久化许可和存储估算不是不丢失数据的保证。不同正式/预览来源之间需要手动导出和导入。

## 可复核测试

`pnpm exec vitest run packages/local-store/test/store.test.ts` 覆盖事务恢复、活跃持有者保护、两个数据库连接互斥、旧修订拒绝、分支保留、档案隔离、凭证设置拒绝、去重与最后引用删除、预算失败整体回滚、缺失 Blob、错误哈希、确认绑定、备份往返与重复导入、重新审查确认失效、中断导入清理、CRC/路径/角色/压缩方法拒绝及遗留暂存清理。

上下文测试 `tests/unit/context.test.ts` 另覆盖不可变请求、跨档案/混合会话/断裂分支拒绝、附件按内容去重与稳定引用、上下文起点后的附件重新注入、显式排除、失效 Blob/确认、策略变化和移动附件后的明确超限。

存储单元测试使用 fake-indexeddb。Chromium 端到端测试另外通过了真实 IndexedDB Blob、Web Locks 双标签页互斥、备份往返、较新 Schema 只读恢复、刷新恢复和写入故障注入。实际磁盘配额不足、阻塞升级、持久化许可及不同设备后台冻结仍须按发布验收表执行。
